# gruper (рабочее название)

Универсальный no-code сервис для очистки, ручной группировки и сведения «грязных» табличных отчётов (Excel/CSV, включая выгрузки из 1С и маркетплейсов).

## Статус

Проектирование (архитектура, стек, валидация спроса) в основном завершено. **Код пишет Claude Code** (подтверждено пользователем). Первый реальный модуль уже есть: `core/reconcile.py` — рекурсивный rollup по дереву категорий + `tests/test_reconcile.py` (30/30 тестов проходят, включая property-based проверку на 20 случайных деревьях) — гарантия, что «Итого = сумма всех строк» математически никогда не нарушится.

## Каталог услуг (10 пунктов, каждый закрывает проверенную боль)

1. Группировка/категоризация (дерево, ручной мэппинг, «ножницы») — ядро
2. Несколько источников (консолидация / сравнение по периодам)
3. Сверка двух файлов на расхождения
4. Развернуть сводную (Unpivot)
5. Объединение листов одного файла как источника
6. Извлечение таблиц из живых (не сканированных) PDF в тот же движок
7. Сравнение PDF (Compare/Redline)
8. Разбивка PDF по маркеру
9. Водяные знаки при скачивании PDF
10. Mail Merge (Excel → N именных PDF-документов)

Все 10 доступны на любом тарифе — тарифы различаются только объёмом (см. монетизацию ниже), не набором услуг.

## Ключевые решения (зафиксированы в обсуждении)

- **Ручной мэппинг, без ИИ на ядре.** Пользователь сам строит дерево групп/подгрупп (произвольная вложенность, значение переносится только в лист — не в промежуточный узел) и вручную распределяет уникальные значения. **Никаких автоматических подсказок объединения похожих значений** — пользователь явно отклонил вариант с подсказками, разнос строго вручную (чекбоксы + bulk-перенос, без единого предложения от алгоритма).
- **Множественные источники.** Можно загрузить несколько файлов сразу — либо консолидировать в один итог, либо сравнивать по периодам (обе механики строятся на одном и том же разобранном наборе данных).
- **Стек (обоснован реальными бенчмарками):**
  - Парсинг файлов — `python-calamine` (Rust-биндинг), покрывает .xls/.xlsx/.xlsm/.xlsb/.ods одной библиотекой — в ~21 раз быстрее openpyxl.
  - Обработка данных — **Polars** (не pandas) — на одинаковой задаче в ~3.9 раза быстрее pandas, измерено локально.
  - Нечёткое сравнение — `RapidFuzz` с блокировкой по извлечённым цифрам перед сравнением (наивное сравнение «каждый с каждым» на 45 000 уникальных значений — 51 сек; с блокировкой — 0.09 сек).
  - CSV-кодировка — автоопределение (UTF-8 → Windows-1251) через `charset-normalizer`, разделитель `;` и десятичная запятая — обязательно для выгрузок из 1С.
  - Очередь задач — Redis + RQ (не Celery — избыточен для целевого сервера).
  - Backend — FastAPI, БД — PostgreSQL.
- **Формат вывода:** два листа — «Детализация» (исходные строки + путь по дереву групп + источник) и «Итоги» (свод с подытогами по каждому уровню, включая явную строку «Не распределено» для сверки).
- **Монетизация (финальная схема — деление по ОБЪЁМУ, не по фичам):** ВСЕ 10 услуг каталога (группировка, несколько источников, сверка, unpivot, объединение листов, PDF-таблицы, PDF Compare, разбивка PDF, водяные знаки, Mail Merge) доступны на любом тарифе, включая бесплатный. Разница только в лимитах: Бесплатно — 1 сохранённый проект, файл до 20 МБ, PDF до 10 стр/мес, реклама. Профи (~990 ₽/мес) — безлимит проектов, файл до 100 МБ, PDF до 200 стр/мес, **реклама остаётся** (не убираем — не главный триггер оплаты, реальный крючок это лимиты). Разовая оплата ~199-299 ₽ — способ оплаты (не отдельная линейка), доступ к лимитам «Профи» на 1 файл без регистрации/сохранения.
- **Не feature-gating, не полный конструктор — фиксированный тариф + докупка объёма.** Feature-gating (PDF только в дорогом тарифе) — отклонено пользователем как нечестное разделение, раз все 10 услуг реально нужны и закрывают проверенные боли. Полный конструктор (галочки по функциям) — по-прежнему отклонён, конкуренты так не делают, паралич выбора для нетехнической аудитории. Компромисс: 2 фиксированных тарифа (Бесплатно/Профи) + докупка объёма сверху («+5 проектов», «+100 PDF-страниц») для граничных случаев.
- **Архитектура интерфейса:** «Проекты» (сохранённое дерево+словарь под повторяющийся тип отчёта, источники — Excel/CSV/PDF-таблицы равноправны) отдельно от «Инструментов» (разовые утилиты без сохранения — Unpivot, Compare, Mail Merge, Split, Watермарк).
- **Защита накопительных лимитов от абьюза (смена IP/куки).** Разовая обработка файла (без сохранения) — доступна анонимно, тут нечего защищать (лимит на файл не накопительный). А вот сохранение «Проекта» и месячные квоты (PDF-страницы) обязательно требуют email-аккаунта — анонимная сессия физически не может владеть сохранённым проектом. Полностью защититься от множественных email нельзя (как и у любого SaaS), но обход бесплатного лимита стоит абьюзеру повторной ручной пересборки дерева категорий (30-60 мин) — то есть теряется именно та выгода, ради которой стоило бы платить. Доп. меры (снижают шум, не решают полностью): подтверждение email, rate-limit регистраций с одного IP/сутки.
- **Регистрация — «мягкий email», не анонимность и не полная регистрация.** Первая разовая обработка без сохранения — анонимна (вирусный магнит для холодного трафика из поиска/Telegram, порог входа = 0, load-bearing для всей стратегии роста). Сохранение Проекта — только email без пароля/подтверждения на этом шаге (не полноценная регистрация) — минимальное трение, но уже даёт лид-базу и закрывает накопительные лимиты.
- **Лимит файла (20 МБ) — не главный рычаг монетизации.** Конкуренты держат 10-100 МБ на free tier, наши 20 МБ — середина диапазона. Но типичный реальный отчёт (по нашим же бенчмаркам: 20 МБ ≈ 300 000 строк) — это 1-5 МБ, то есть подавляющее большинство обычных пользователей лимит никогда не увидят. Главный рычаг — «1 бесплатный проект», не размер файла. Точное число не критично — смотреть реальное распределение размеров после запуска, не гадать заранее.

## Пробелы, не закрытые монетизацией (нужно решить до платежей, не позже)

- Командный доступ к одному Проекту (2-3 сотрудника на одну бухгалтерию) — сейчас 1 аккаунт = 1 человек, решить до Фазы 2.
- Годовая оплата со скидкой — не заложена, стандартная механика для снижения оттока.
- Политика возврата/отмены — не обсуждена, требуется по закону и для подключения ЮKassa.
- API-доступ для агентств (обработка отчётов для многих клиентов) — не блокирует MVP, будущий рычаг для верхнего тарифа по объёму/доступу, не по фичам.

## Фаза 3 — небольшие доработки поверх готового движка (подтверждены пользователем)

- **Сверка взаиморасчётов между двумя файлами** — тот же движок fuzzy-match + ручной мэппинг с памятью, вывод — список расхождений вместо суммы по группе.
- **Объединение нескольких листов одного файла** как ещё одного источника (тот же механизм «несколько источников», что уже спроектирован для консолидации/сравнения периодов).
- **Разворот сводных таблиц (Unpivot/Reverse Pivot)** — `pandas.melt`/эквивалент в Polars: превращает двумерную сводную таблицу (товары строками, месяцы столбцами) в плоский список для загрузки в 1С/CRM. Реальная массовая боль, технически копеечно.
- **Генератор документов из Excel (Mail Merge)** — пользователь размечает переменные в своём PDF/Word-шаблоне договора, загружает Excel на N строк, получает архив из N именных PDF-договоров. Отдельный по объёму модуль, не «заодно» с ядром.
- **Умная разбивка PDF по маркеру** — большой PDF (сотни страниц, накладные разных клиентов подряд) режется на отдельные файлы по повторяющемуся текстовому маркеру («УПД №», смена ИНН), автоматически именуется. Детерминированный код, без ИИ.
- **Динамические водяные знаки при скачивании** — при скачивании PDF/прайс-листа из личного кабинета на каждую страницу накладывается прозрачный водяной знак с ID/именем/IP скачавшего сотрудника — защита от слива баз данных для дистрибьюторов.

## PDF — отдельное направление (не «заодно» с Excel-ядром)

- **Сравнение документов (Compare/Redline)** — единственная PDF-фича из «дорогих премиум» идей, признанная стоящей: свободная ниша (ни iLovePDF, ни Smallpdf так не делают), детерминированный текстовый diff по координатам, без ИИ.
- **Извлечение таблиц из «живых» (не сканированных) PDF** в тот же движок группировки — конкуренты (iLovePDF/Smallpdf) сами ломают такие таблицы и оставляют пользователя разбираться в сыром Excel; мы можем отдавать кривой результат прямо в уже готовый экран ручной разметки.
- **PDF со сканов (OCR + ручная разметка рамок на изображении)** — технически возможно без оплаты AI-токенов (Tesseract — не LLM), но это ЗАМЕТНО более сложный отдельный модуль (предобработка изображений, борьба с перекосом скана) — не решено, не в плане, требует отдельной оценки, если возникнет спрос.

### PDF — реально протестировано (не только описание библиотек, как раньше)

Собрал синтетический «счёт»-PDF (реальный текстовый слой, кириллица, без линий-границ — как большинство настоящих накладных) и прогнал через `pdfplumber` и `camelot`, тем же уровнем строгости, что и Excel-бенчмарки:
- **`pdfplumber` в дефолтной конфигурации — 0 извлечённых строк** и на 3000, и на 20 000 строках. Дефолтная стратегия ищет линии-границы таблицы, а на счетах без явных границ это не работает вообще. Нужна явная настройка (`vertical_strategy="text"`), не «из коробки».
- **`camelot` (flavor=stream) — работает и даёт верные данные.** Проверил результат посимвольно по кодам Unicode (не доверяя выводу в консоль Windows, которая манглит кириллицу) — значения извлекаются точно, без потерь и сдвигов по колонкам.
- **Но заметно медленнее Excel.** 20 000 строк / 556 страниц — **34.3 сек** на сильной машине (i5-12600K). С поправкой на целевой сервер (слабее в 3-4 раза) — реалистично **~100-140 сек** на такой объём. PDF-квоты/таймауты очереди нужно закладывать с этим числом, не ожидать той же мгновенности, что у Excel.
- **Проверил и отклонил «более быстрые» альтернативы.** Нашлись Rust-библиотеки с заявлениями «в 10-50 раз быстрее» (pdfsink-rs, pdf_oxide, tablers), но с тревожными признаками: несколько никак не связанных GitHub-аккаунтов (`Mu-L`, `firecrawl`, `pinegap-tech`) публикуют репозиторий с одинаковым названием и текстом описания — похоже на спам/клоны, не независимые проекты. Не беру в стек без реальной проверки на практике. **PyMuPDF тоже проверил и отклонил** — в их же репозитории задокументирован баг: `find_tables()` у PyMuPDF медленнее, чем у pdfplumber ([GitHub issue #2885](https://github.com/pymupdf/PyMuPDF/issues/2885)).
- **Реальное решение — параллелизм по ядрам, не смена библиотеки.** Camelot обрабатывает страницы независимо, значит можно распилить документ на N процессов по числу ядер сервера (3). Измерил по-честному: 3 параллельных процесса дают **34.3с → 21.7с, ускорение в ~1.6 раза** — не в 3 раза, как наивно ожидалось (накладные расходы на старт процессов и импорт camelot/opencv в каждом съедают часть выигрыша). Это бесплатное и честное улучшение (использовать в очереди задач), но не устраняет разрыв со скоростью Excel — PDF всё равно требует реального прогресс-бара, не мгновенного результата.

## Осознанно НЕ делаем

- B2B-кабинеты фирм (иерархия торгпред/супервайзер/город) — отложено, не сейчас.
- Редактирование/замазывание PDF-данных (Redaction) — iLovePDF уже даёт бесплатно + реальный юридический риск при неидеальной реализации (задокументированные утечки через «чёрные прямоугольники»).
- Заполняемые PDF-формы — конкуренты уже дают бесплатно, не отличие.
- Пакетное подписание ЭЦП — недооценённая сложность: хранить закрытый ключ пользователя на своём сервере небезопасно, требует либо браузерного плагина, либо платной облачной подписи КриптоПро DSS — не «просто кнопка».
- Стандартизация адресов/телефонов/ФИО — рынок уже держит DaData.ru (5-10 коп/адрес), переизобретать бессмысленно; если понадобится — интеграция через их API, не своя разработка.
- Удаление метаданных PDF — уже полностью бесплатно у десятков сервисов, нет дифференциации.
- Генератор штрихкодов/этикеток — другая предметная область (печать/склад), размывает фокус.

## Вертикали для лендингов/SEO (не новый код — переупаковка тех же 3 механизмов)

Глубокий проход по болям (банковские выписки, дубли контактов для рассылок, сверка остатков склада, объединение табелей, слияние CRM-баз, сравнение версий отчёта) показал: ни одна не требует новой архитектуры. Всё раскладывается на 3 уже спроектированных механизма:
- **Дерево категорий** (ядро) → категоризация банковской выписки по статьям расходов.
- **Сравнение по периодам** (уже спроектировано) → «что изменилось в отчёте» между версиями.
- **Fuzzy-dedup + несколько источников** (ядро + Фаза 3) → чистка email-баз от дублей перед рассылкой, слияние выгрузок из разных CRM, сверка остатков склада, объединение табелей рабочего времени (метрика — часы, а не деньги/вес — уже поддерживается гибкими метриками).

**How to apply:** каждая строка выше — кандидат на отдельную посадочную страницу («Разобрать банковскую выписку по категориям онлайн», «Объединить CRM-базы без дублей») под тот же самый продукт, без доработок движка. Если появится боль, которая НЕ ложится ни на один из трёх механизмов — только тогда разбирать её как отдельную фичу.

## Приём платежей — самозанятый + Robokassa (не ЮKassa!)

**Исправлено 2026-09-26: ЮKassa отменила автоотправку чеков для самозанятых с 29 декабря** ([vc.ru, подтверждено](https://vc.ru/id671420/2687901-yukassa-otmenila-avtootpravku-chekov-dlya-samozanyatyh)) — то, что я раньше описал как рабочую схему, больше не работает. Оставшиеся у ЮKassa варианты (ручная выписка на каждый платёж, или одним чеком за период) не масштабируются и, по оценке разбиравших это людей, вторая схема «выглядит не совсем легально».

**Меняю рекомендацию на Robokassa.** У них есть отдельный продукт **«Робочеки СМЗ»**, актуальный на 2026 год: подключается разрешением в приложении «Мой налог», дальше чек формируется **автоматически на каждый платёж** без ручных действий — именно то поведение, которое мы изначально хотели от ЮKassa.
- **ИП открывать не нужно** — тот же принцип, авторизация через «Мой налог».
- **Обязательное поле в каждом платеже:** email или телефон плательщика — чек физически некуда отправить без него (это общее требование 422-ФЗ, не специфика конкретного провайдера).
- **До запуска монетизации — проверить актуальные условия Robokassa напрямую** (тарифы/комиссии меняются, как только что показал пример с ЮKassa — не доверять этому описанию слепо через полгода, перепроверять перед реальным подключением).
