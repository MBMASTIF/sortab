# gruper (рабочее название)

Универсальный no-code сервис для очистки, ручной группировки и сведения «грязных» табличных отчётов (Excel/CSV, включая выгрузки из 1С и маркетплейсов).

## Статус

Проектирование (архитектура, стек, валидация спроса) в основном завершено. **Код пишет Claude Code** (подтверждено пользователем). Реальный код уже есть:
- `core/reconcile.py` — рекурсивный rollup по дереву категорий + `tests/test_reconcile.py` (30/30 тестов, включая property-based проверку на 20 случайных деревьях) — гарантия, что «Итого = сумма всех строк» математически никогда не нарушится.
- `core/queues.py` — очередь заданий с жёстким приоритетом (платные всегда впереди бесплатных) + `tests/test_queues.py` (2/2 теста через fakeredis, проверено вживую, не по документации на слово: платное задание, поставленное в очередь вторым, реально обрабатывается первым).
- `core/parsing.py` — загрузка Excel/CSV (calamine + Polars + charset-normalizer) + `tests/test_parsing.py` (5/5, включая настоящий cp1251-файл). Тест поймал живой баг: `charset-normalizer` спутал Windows-1251 с ивритом (cp1255) на коротком образце — починено явным приоритетом cp1251 (мы знаем аудиторию — 1С).
- `core/tree.py` — CRUD дерева групп: только-лист-присвоение, защита от удаления непустых групп + `tests/test_tree.py` (11/11, включая сквозной тест совместимости с `reconcile.py`).
- `core/export.py` — сборка двух листов («Детализация»+«Итоги») в реальный .xlsx + `tests/test_export.py` (4/4, файл читается обратно и сверяется по значениям, не просто «не упало»).

- `core/session.py` — оркестрация рабочей сессии (парсинг → колонки → уникальные значения → присвоение → сверка) + `tests/test_session.py` (5/5).

**Все 5 модулей ядра конвейера готовы и протестированы: 60/60 тестов по всему проекту** (57 было + 3 новых на `parse_file_raw()`, см. ниже).

### FastAPI-бэкенд поверх ядра — готов и протестирован (27.09.2026)

Все 8 обязательных эндпоинтов реализованы в `backend/main.py`, обёрнуты вокруг уже готового `core/*` без переписывания логики: `POST /api/upload`, `POST /api/session/{id}/columns`, `GET .../entities`, `POST .../groups`, `DELETE .../groups/{id}`, `POST .../assign`, `GET .../summary`, `GET .../export`.

- **Проблема «заголовок не в строке 0» решена в `core/parsing.py`, не на уровне API.** Добавлена `parse_file_raw()` — читает файл с `has_header=False` (и для Excel/calamine, и для CSV), отдаёт вообще все строки как данные с généric-именами колонок. `upload.html` показывает эту сырую сетку, пользователь кликает по настоящей строке-заголовку, `backend/columns.py::finalize_columns()` отрезает всё до неё включительно и превращает её значения в реальные имена колонок. Решил так, а не патчить `parse_file()` флагом — это отдельная, самостоятельно тестируемая функция, существующие тесты и поведение по умолчанию не тронуты (60/60 всё ещё зелёные).
- **Redis-хранение сессии между HTTP-запросами** (`backend/session_store.py`): DataFrame — как Arrow IPC bytes (`write_ipc`/`read_ipc`, почти нулевые накладные расходы — стандартная практика для Polars), дерево групп + assignment (включая `Decimal`-доли) — как JSON, `Decimal` сериализуется строкой и парсится обратно через `Decimal(str(...))` — float ни разу не касается денег на этом пути. Обе части лежат в одном Redis-хэше на `session_id` (uuid4), TTL 24 часа и обновляется при каждом сохранении — анонимные сессии сами вычищаются, не копятся вечно.
- **Redis-клиент переиспользует конвенцию `core/queues.py`** (соединение — параметр, не глобал) через FastAPI-зависимость `get_redis()`, которая в тестах подменяется на `fakeredis` — весь набор тестов бэкенда гоняется без живого Redis-сервера.
- **Ошибки домена превращены в осмысленные HTTP-коды, не в голый 500**: `GroupNotEmptyError` → 409 (тот же текст, что и `alert()` в прототипе `app.html`), `NotALeafError` → 409, неизвестная сессия → 404, не выбраны колонки → 409, некорректный `header_row_index`/дубли групп/прочие доменные ошибки → 400/409 по смыслу.
- **`backend/tests/test_api.py` — 7/7 тестов через `TestClient` + `fakeredis`, реальный прогон** (не пересказ): полный сценарий на настоящем .xlsx с декоративной строкой перед заголовком (через openpyxl, не `write_excel()` — у него своя генерируемая строка заголовка, которая замусорила бы именно этот тестовый кейс) → upload → columns → entities → вложенное дерево (Одежда > Носки/Бельё, Обувь) → bulk-assign тремя отдельными вызовами → сверка (`носки чёрные` 4500+3000=7500, `Одежда`=10900, `Обувь`=32000, `Не распределено`=8900 за «шапка вязаная», ИТОГО=51800 — ровно сумма всех строк файла) → экспорт скачан и прочитан обратно через `openpyxl`, числа в реальных ячейках сверены построчно (не только API-ответ). Отдельно проверены обязательные негативные пути: удаление непустой группы → 409 без потери данных, присвоение в не-лист → 409, запрос к несуществующей сессии → 404 на каждом эндпоинте, неподдерживаемый тип файла → 400, `header_row_index` вне диапазона → 400.
- **`requirements.txt` дополнен:** `python-multipart` (нужен FastAPI/Starlette для парсинга multipart-загрузки файла — был не объявлен, хотя эндпоинт на него рассчитан) и `uvicorn` (запуск ASGI-приложения вне тестов).
- **Полный прогон всего проекта: 67/67 тестов зелёные** (60 core + 7 backend).
- **Осознанно не в этой фазе:** JWT/аккаунты (сессии анонимны эфемерны), тарифы/лимиты, PDF-эндпоинты, RQ-очередь (обработка синхронная — файлы маленькие), реальное сохранение «Проектов» в Postgres (`dashboard.html` остаётся на моках).

### PDF как источник в том же конвейере — готово и протестировано (27.09.2026)

`core/parsing.py::_read_pdf_raw()` добавляет `.pdf` в `parse_file_raw()` (`camelot`, `flavor="stream"` — уже обоснованный выбор, см. выше) и отдаёт РОВНО ту же форму (2D-сетка, `has_header`-агностично), что и Excel/CSV — весь остальной конвейер (`backend/main.py`, `backend/columns.py::finalize_columns()`, `design-prototype/upload.html`) заработал без единой правки логики, только `accept=".pdf"` во фронтенде.

- **Многостраничные таблицы.** Camelot отдаёт одну `Table` на страницу. Если у всех страниц совпадает первая строка (повторяющийся заголовок — типичный паттерн многостраничных отчётов) — склеиваю в одну сетку, дубли заголовка со 2+ страницы убираю. Если заголовки расходятся ИЛИ camelot нашёл разное число колонок на разных страницах — не гадаю: конкатенирую как есть (с паддингом коротких строк), отдаю пользователю на уже готовый экран выбора строки-заголовка. Решение в `core/parsing.py::_glue_pdf_page_grids()`, покрыто отдельными юнит-тестами на все 4 ветки.
- **Два реальных бага найдены и починены живым тестированием, не предположены:**
  1. Camelot/`playa` мапит исходный файл через `mmap`; из-за цикла ссылок в объектном графе mmap не освобождался даже после удаления всех локальных ссылок — `os.unlink()` временного файла падал с `PermissionError` на Windows. Чинится `gc.collect()` после копирования данных в обычные Python-строки.
  2. При живом smoke-тесте через curl против задеплоенного сервера словил РЕАЛЬНЫЙ необработанный 500: один из вариантов битого PDF даёт не `playa.exceptions.PDFException` (который уже ловился), а голый `StopIteration` из ридера трейлера `playa` — пересекая границу `async def`-эндпоинта, PEP 479 превращает его в `RuntimeError: coroutine raised StopIteration`. Прогнал 7 разных вариантов битых байт, чтобы не гадать — нашёл ещё и третий тип (`ValueError` от `mmap` на пустом файле). Теперь `_read_pdf_raw()` ловит все три, единообразно превращая в `UnsupportedFileError` → 400.
- **Тестовые фикстуры** (`backend/tests/fixtures/pdf_*.pdf`) сгенерированы через `reportlab` с явно зарегистрированным кириллическим TTF-шрифтом (Helvetica по умолчанию не умеет кириллицу — уже пойманная в проекте грабля, см. `generate_fixtures.py`): таблица без рамок (доказывает, что `flavor="stream"` реально нужен), таблица на 3 страницы с одинаковым заголовком (доказывает склейку), пустая страница (нулевой кейс).
- **`.gitattributes` добавлен** (`*.pdf`/`*.xlsx`/`*.xls`/`*.ods` → `-text`): git по умолчанию угадывает binary/text по наличию NUL-байта в первых ~8000 байт — пустая PDF-страница без встроенного шрифта/картинки его не содержит и попала под конвертацию LF→CRLF при `git add`, что реально ломает бинарник при клонировании с `core.autocrlf=true` (дефолт на Windows). Не гипотеза — поймано `git add` вживую.
- **Прогнано на живом задеплоенном сервере, не только локально**: `pytest` (90/90, включая Linux/Python 3.12, БЕЗ Ghostscript в системе — подтверждено, что `flavor="stream"` его действительно не требует) и полный сценарий через Playwright против `http://195.161.62.21/upload.html` (загрузка PDF → выбор колонок → `app.html` → распределение всех 12 значений → сверка 79 390,55 ₽ = группа = «Не распределено» 0 → скачанный `.xlsx` прочитан обратно и сверен по значениям, не по виду). Также найден и добавлен в `requirements.txt` пропущенный тестовый пакет `httpx2` (нужен `TestClient` на более новой `starlette` живого сервера).
- **Осознанно не в этой фазе:** остальные 4 PDF-утилиты каталога услуг (Сравнение, Разбивка по маркеру, Водяные знаки, Mail Merge) — отдельная фаза; месячная накопительная PDF-квота (10 стр./мес на Free) — требует реального биллинга, которого пока нет; RQ-очередь для PDF-джобов — весь конвейер синхронный, PDF сделан так же для консистентности.

### Инструменты — Unpivot и Compare — готовы и протестированы (27.09.2026)

Первые два реальных «Инструмента» из каталога (README «Каталог услуг» пп. 3-4 / «Фаза 3»): `design-prototype/dashboard.html`'s карточки «Развернуть сводную» и «Сравнение файлов» больше не мёртвые div — ведут на `unpivot.html`/`compare.html`, оба задеплоены и рабочие. Явно НЕ часть конвейера категоризации — без сессии-«Проекта», без сохранения, доступны анонимно.

- **`core/unpivot.py`** — тонкая обёртка над нативным `DataFrame.unpivot()` (Polars ≥1.44 переименовал `.melt()`), плюс валидация ролей колонок (мин. 1 id-колонка, мин. 2 value-колонки) и та же нормализация десятичной запятой, что уже используется для денежной колонки в основном конвейере.
- **`core/compare.py`** — двухпроходное сопоставление сущностей между файлами: сначала точное совпадение по нормализованному ключу (trim+lowercase), затем `RapidFuzz` с блокировкой по извлечённым цифрам для всего, что не совпало точно — тот же паттерн, что уже обоснован бенчмарком в README. Деньги — `Decimal` от начала до конца, ни разу float.
- **Архитектурное решение по хранению между preview и commit (осознанный выбор, не догадка):** первая версия держала распарсенный DataFrame в памяти процесса по одноразовому токену — рассуждение «это не Project-сессия, значит не нужен Redis» было верным по форме данных, но неявно предполагало один процесс. Проверка живого `systemd`-юнита (`systemctl cat gruper-backend`) ДО того как считать это готовым показала `--workers 2` — токен, выданный воркером 1, невидим воркеру 2, что превратило бы фичу в рандомно падающую (~50% запросов). Починено: `backend/tools_store.py` теперь хранит байты (Arrow IPC) в Redis с TTL 15 минут через тот же `get_redis`/`fakeredis`-паттерн, что и `session_store.py` — но НЕ full session (нет `TreeStore`, нет `finalized`, нет `header_row_index`), только `token -> bytes`.
- **API:** `POST /api/tools/preview` (общий для обоих инструментов upload+preview шаг, тот же `parse_file_raw()`, что у основного конвейера) → `POST /api/tools/unpivot` (commit, отдаёт `.xlsx` напрямую) и `POST /api/tools/compare` (JSON с построчным результатом + сводкой) / `POST /api/tools/compare/export` (тот же вход, пересчитывает и отдаёт `.xlsx` — сознательно без второго токена на результат, входные файлы этого класса дешёво пересчитать заново).
- **UI:** `unpivot.html` переиспользует визуальный паттерн `upload.html` (клик по заголовку колонки), но с 3-состоянием на колонку (ничего → «как есть» → «развернуть» → сброс) вместо жёстких 2 слотов — потому что id/value-колонок может быть сколько угодно. `compare.html` — 3 шага (файл A → файл B → результат), для каждого файла переиспользован ровно тот же 3-стейт entity/metric-пикер, что в `upload.html`, только параметризован по стороне.
- **114/114 тестов** (было 90/90): core-уровень (`tests/test_unpivot.py`, `tests/test_compare.py` — включая независимо просчитанный 4-статусный сценарий сверки: совпадает/расхождение/только-A/только-B), `backend/tests/test_tools_store.py` (включая тест, что два разных инстанса `ToolFileStore` на одном Redis-соединении видят один и тот же токен — ровно тот сценарий, который ломался до фикса), `backend/tests/test_tools_api.py` (полный HTTP round-trip через `TestClient`+`fakeredis` для обоих инструментов).
- **Прогнано на живом сервере, не только локально:** `pytest` 114/114 (Linux/Python 3.12) и полный Playwright-сценарий против `http://195.161.62.21/unpivot.html` и `.../compare.html` с реальными тестовыми файлами — для Unpivot: 2 товара × 3 месяца → 6 строк, сумма 9800 сошлась в скачанном файле; для Compare — специально собранный файл A/B с одной сущностью-совпадением, одной расхождением (5000→5500, разница 500), одной только в A (ЗАО Вектор, 777.77), одной только в B (ООО Заря, 300) — все 4 статуса подтверждены и на экране, и в скачанном `.xlsx`, посчитаны заранее вручную, не поверено на слово реализации. Ноль ошибок в консоли (кроме не относящегося к делу 404 на `favicon.ico`).
- **Осознанно не в этой фазе:** Mail Merge, Разбивка по маркеру, Водяные знаки — остальные три карточки на дашборде теперь явно помечены «Скоро» (`.is-disabled`) вместо вида кликабельных.

### Инструменты — Mail Merge, Разбивка по маркеру, Водяные знаки — готовы и протестированы (27.09.2026)

Последние три карточки из каталога «Инструментов» (README «Каталог услуг» пп. 8-10 / Фаза 4) реализованы, задеплоены и включены на дашборде — теперь все 10 пунктов каталога услуг закрыты кодом. Как и Unpivot/Compare: без сессии-«Проекта», без сохранения, доступны анонимно.

- **Новая зависимость на уровне страниц PDF — выбор сделан бенчмарком, не по описанию.** Кандидаты: `pypdf` (активно поддерживаемый форк PyPDF2) и `pikepdf` (обёртка над libqpdf). Измерил на задачах именно этой фазы (наложение водяного знака на синтетический 200-страничный PDF с реальной кириллицей через reportlab): `pypdf` — 0.222 с, `pikepdf` — 0.081 с (pikepdf быстрее в ~2.7 раза на водяных знаках). Но Разбивка по маркеру принципиально требует извлечения ТЕКСТА со страницы для поиска маркера — у `pikepdf` такой возможности нет вообще (проверено вживую: `hasattr`-проверка на текстовое API у его объектов Page/Pdf — `False`, это структурный редактор поверх libqpdf, не движок вёрстки текста). `pypdf` даёт `page.extract_text()` из коробки и достаточно быстр на обеих задачах — решил использовать один пакет на оба инструмента вместо двух: 140 мс разницы на 200 страницах не имеют значения при реальных масштабах проекта (единицы страниц на бесплатном тарифе), а одна хорошо изученная зависимость проще в поддержке, чем две. Подробности и код бенчмарка — в докстринге `core/watermark.py`.
- **`core/mailmerge.py`** — простой текстовый шаблон с плейсхолдерами `{{Поле}}`, без попытки заполнять произвольно загруженную PDF/Word-форму (сознательно вне охвата этой фазы — распознавание полей формы и совместимость шрифтов/вёрстки чужого документа значительно сложнее и хрупче простого шаблона, скомпонованного в новый PDF через `reportlab`). Валидация: шаблон должен содержать хотя бы один плейсхолдер, и каждый плейсхолдер обязан ссылаться на реально существующую колонку файла — иначе понятная ошибка до генерации, а не N сломанных документов. Перенос строки в шаблоне и word-wrap по реальной ширине символов (`pdfmetrics.stringWidth`, не фиксированное число символов) с автоматической пагинацией на несколько страниц для длинного текста.
- **`core/pdf_split.py`** — режет PDF по каждому вхождению текстового маркера (точное подстроковое совпадение, с учётом регистра — так пользователь сам контролирует точность разбивки: «Накладная №» разрежет грубее, чем «Накладная №0042»). Страницы до первого вхождения маркера не теряются молча — попадают в отдельную первую часть. Если маркер не найден ни разу — явная ошибка, а не пустой архив (это было отдельным требованием, проверено тестом).
- **`core/watermark.py`** — полупрозрачный (alpha ≈0.35) диагональный текст поверх каждой страницы через наложение `reportlab`-страницы (`page.merge_page`, актуальный неустаревший API — `PdfWriter(clone_from=reader)` + слияние на странице, уже привязанной к writer'у, а не устаревший с версии 6.x путь через голый `PdfReader`). Размер шрифта подбирается под диагональ конкретной страницы (`pdfmetrics.stringWidth`-калибровка), а не фиксирован — короткий штамп «КОПИЯ» и длинный email не обрезаются и не теряются на разных форматах страниц. Оверлей на разные размеры страниц (реальный некрасивый случай: один документ, где страницы вперемешку A4/Letter) кэшируется по размеру, не перегенерируется на каждую страницу.

### Несколько независимых деревьев категорий в одной сессии — готово и протестировано (27.09.2026)

Пользователь явно расширил задачу поверх изначального ТЗ (подтверждено через уточняющий вопрос): не «1 колонка деревом + N сырых разбивок», а **пользователь сам выбирает, сколько колонок файла категоризировать вручную** (1 или больше), и каждая выбранная колонка получает СВОЙ независимый экран/дерево — например «Товар» со своими товарными категориями И «Клиент» со своими категориями клиентов одновременно, в одной сессии, на одном и том же наборе строк.

- **`core/session.py`** — `Session.entity_column: str | None` + `tree: TreeStore` заменены на `categorized_columns: list[str]` + `trees: dict[str, TreeStore]` (одно независимое дерево на колонку). `metric_column` остаётся один — та же сумма просматривается через разные деревья. Известные значения (`_previously_known_entities`) теперь тоже per-колонка: то, что «Иванов» уже распределён в дереве «Товар», ничего не говорит о дереве «Клиент». `core/tree.py::TreeStore` и `core/reconcile.py::rollup()` переиспользованы БЕЗ единой правки — каждое дерево это просто отдельный экземпляр уже готового движка.
- **Колонки-разбивки (`dimension_columns`) остались отдельной третьей ролью** — колонка без дерева, просто едет вместе со строкой как контекст (например «Менеджер»), используется для разреза `core/export.py::build_breakdown_sheet()` (нативный Polars `.group_by(...).agg(pl.sum(...))`, не Python-цикл по строкам — быстро на реальных тысячах строк 1С). Единственный осознанный компромисс: суммирование внутри ЭТОЙ разбивки идёт по `Float64` (денежная колонка в Polars всегда float, см. `core/parsing.py::normalize_decimal_comma`), но каждая готовая ячейка агрегата сразу проходит через `Decimal(str(...))` — тот же приём, что уже применяется в `core/session.py::rows_for_rollup()`. **Сам глобальный «Итого/По группам/Не распределено» (`core/reconcile.py::rollup()`) не тронут вообще** — он вызывается по одному разу НА КАЖДОЕ дерево со своим набором assignment, и сходится независимо для каждого дерева к одной и той же сумме файла (проверено и юнит-тестом, и живым Playwright-прогоном ниже).
- **`core/export.py`** — `build_multi_tree_detail_sheet()` добавляет путь по дереву для КАЖДОЙ категоризируемой колонки, с префиксом по имени колонки (`"Товар: Группа 1"`, `"Клиент: Группа 1"`, чтобы пути разных деревьев не путались), плюс колонки-разбивки вынесены вперёд. `export_workbook()` расширен `extra_summary_sheets`/`extra_breakdown_sheets` (доп. листы «Итоги — {колонка}» / «Разбивка — {колонка}» для 2+ деревьев), при этом **старый вызов с одним деревом даёт абсолютно тот же файл, что и раньше** (проверено отдельным тестом на обратную совместимость). Имена листов Excel защищены от превышения 31 символа и служебных символов (`_safe_sheet_name()`) — реальное имя колонки 1С может быть длинным.
- **`backend/main.py`** — почти все эндпоинты дерева получили `{column}` в пути: `GET/POST /session/{id}/groups/{column}`, `DELETE .../groups/{column}/{group_id}`, `POST .../assign/{column}`, `GET .../entities/{column}`, `GET .../summary/{column}` (сверка отдельно на каждое дерево), `GET .../breakdown/{column}` (новый). Новый `GET /session/{id}/columns` — чтобы `app.html` после редиректа узнал, какие колонки категоризированы (для вкладок). `POST .../columns` принимает `categorized_columns: list[int]` вместо одного `entity_column`, плюс `dimension_columns: list[int]`. `backend/columns.py::finalize_pipeline_columns()` — новая функция для этого (старая `finalize_columns()` не тронута, ей по-прежнему пользуется Compare, которому чужда идея нескольких деревьев).
- **Порядок категоризируемых колонок = порядок колонок В ФАЙЛЕ (по индексу), не порядок кликов на upload.html.** Осознанный выбор: детерминированный и стабильный между перезагрузками страницы результат важнее, чем запоминание последовательности кликов пользователя. Тот же порядок используется и для вкладок на `app.html`, и для присвоения имён листов при экспорте (первая по позиции колонка получает обратно-совместимые имена «Итоги»/«Разбивка», остальные — «Итоги — {колонка}»).
- **`backend/db.py` + `backend/projects_store.py`** — Проект теперь может хранить больше одного дерева: `tree_json` стал `{имя_колонки: {groups, assignment}}` (было — дерево одно на весь проект), плюс новая колонка `categorized_columns`. `entity_column` в БД сохранён ради обратной совместимости карточки проекта на дашборде (= первая категоризируемая колонка). Подгрузка проекта в сессию (`load_project_into_session`) применяет каждое сохранённое дерево к одноимённой колонке сессии; колонка, которой в текущем файле нет — пропускается, не ошибка.
- **Фронтенд.** `upload.html`: клик по колонке — 4-стейт цикл (ничего → «категоризировать» → «разбивка» → «сумма» → ничего), «категоризировать» и «разбивка» — любое число колонок, «сумма» — одна (переиспользован паттерн `unpivot.html`'s per-column role array, расширен третьей ролью с ограничением уникальности). `app.html`: состояние (сущности/дерево/выборка/сверка) стало per-колонка (`columnState`), вкладки над деревом (скрыты при ровно одной категоризируемой колонке — старый однодеревный экран выглядит буквально так же, как раньше), переключение вкладки не теряет прогресс других вкладок (все деревья загружаются заранее). Панель «Разбивка» (кнопка видна только если выбраны колонки-разбивки) — простая таблица под деревом, не мешает существующему рабочему экрану.
- **144 → 157 тестов** (+13): `tests/test_session.py` переписан под несколько деревьев (включая тест, что известность значения не течёт между колонками, и что два дерева сходятся к одной сумме файла независимо), `tests/test_export.py` — новые тесты на `build_multi_tree_detail_sheet`/`build_breakdown_sheet`/доп. листы экспорта (суммы разбивки посчитаны вручную заранее, не поверены implementation'у на слово), `backend/tests/test_api.py` и `test_projects_api.py` переписаны под новый API + новый сценарий на 2 дерева одновременно (включая тест, что id группы одного дерева не работает в другом — действительно раздельные `TreeStore`) и на сохранение/загрузку Проекта с 2 деревьями.
- **Прогнано на живом сервере, не только локально.** `pytest` 157/157 на самом сервере (Ubuntu 24.04/Python 3.12, `sudo -u gruper venv/bin/python -m pytest`). Полный Playwright-сценарий против `https://sortab.ru` на синтетическом файле (Менеджер/Клиент/Товар/Выручка, вымышленные данные, структура — по образцу `decorative_header_1c.xlsx`: декоративная строка перед реальным заголовком): категоризация Товара (Носки/Остальное) И Клиента (Крупные) ОДНОВРЕМЕННО, каждое дерево сверено независимо (Товар: 8700+44300=53000, 0 не распределено; Клиент: 19800 в «Крупные», 33200 не распределено — ИП Кузнецов, и то и другое = та же сумма файла 53000), Разбивка (Менеджер × Товар-дерево) сверена на все 4 комбинации против ручного расчёта, экспорт скачан и прочитан обратно (5 листов: Детализация + Итоги/Итоги — Товар + Разбивка/Разбивка — Товар). **Отдельно прогнан прежний однодеревный сценарий** (1 категоризируемая колонка, без разбивок) — убедиться, что старый путь выглядит и считает буквально как раньше: вкладки и кнopка «Разбивка» скрыты, экспорт — те же 2 листа «Детализация»/«Итоги», что и до этой фазы.
- **Осознанно не в этой фазе:** загрузка НЕСКОЛЬКИХ файлов сразу (консолидация/сравнение периодов, п. 2 каталога услуг) — упомянута пользователем как следующий логичный шаг, но отдельная задача, не смешивается с этой; карточка проекта на дашборде показывает только первую категоризируемую колонку (`entity_column`), не полный список — минорное косметическое ограничение, не баг; порядок вкладок/листов по позиции колонки в файле, не по кликам — см. выше, осознанный выбор.

### Автораспознавание иерархических отчётов 1С + несколько сумм одновременно — готово и протестировано (28.09.2026)

**Иерархические отчёты 1С (главное в этой фазе).** Реальная находка (не гипотеза — проверено вживую на настоящем файле пользователя, 4290 строк): 1С может экспортировать отчёт НЕ плоской таблицей, а «раскрытым деревом группировки» — Менеджер → Клиент → Точка → Товар, где каждый уровень вложенности это ОТДЕЛЬНАЯ СТРОКА в том же столбце A, а уровень закодирован в Excel-атрибуте `alignment.indent` (0/2/4/6). Сумма всех строк самого глубокого уровня (листьев) сходится со строкой «Итого» до копейки.

- **`core/hierarchical.py`** — новый модуль, используется ТОЛЬКО через `openpyxl` (не `python-calamine`, обычный быстрый движок проекта) — `calamine` вообще не даёт доступа к стилям ячеек, а `indent` это именно стиль. Осознанное, документированное исключение из «calamine-first»-правила, платится только на Excel-загрузках, и то не на каждой (только `.xlsx`/`.xlsm` — legacy `.xls`/`.xlsb` `openpyxl` не читает, там просто продолжает работать обычный `parse_file_raw()`).
- **Детекция консервативная по конструкции, никогда не форсирует догадку**: возвращает `None` (откат на обычный путь `parse_file_raw()` + ручной выбор колонок), если распознан только один `indent` (обычный плоский файл), если не нашлась строка «Итого» для проверки, или если сумма листьев не сошлась с «Итого» ровно через `Decimal`.
- **Извлечение названий уровней/метрик — эвристика с честным fallback.** Названия уровней («Торговый агент», «Контрагент», …) ищутся как ПОЛНАЯ последовательность из N подряд идущих непустых строк столбца A с индентами по возрастанию 0→2→4→…, у которых ВСЕ метрики пустые (включая последнюю — самую глубокую). Это специально отсекает реальный случай «у менеджера всего один клиент, у клиента всего одна точка, у точки всего один товар» — тоже даёт подряд идущие 0/2/4/6, но последняя (листовая) строка там ВСЕГДА содержит настоящие цифры, чего не бывает у легенды 1С. Покрыто отдельным regression-тестом. Не нашли уверенно — название уровня становится «Уровень N», без падения.
- **Найден и обойдён ещё один реальный баг** (не тот же, что раньше у этого источника, но того же класса): часть файлов 1С называет часть архива `xl/SharedStrings.xml` (с большой S) вместо стандартного `xl/sharedStrings.xml`, из-за чего `openpyxl.load_workbook()` падает `KeyError`. Обход — переzip'овать файл с исправленным регистром ИМЕННО этой записи, и только после того как обычное открытие реально упало с этой ошибкой (на нормальном файле путь не трогается вообще).
- **Интеграция — без единой правки остального конвейера.** `detect_and_unflatten()` отдаёт `ParsedFile`, повторяющий ровно ту же форму, что и `parse_file_raw()` для обычного Excel: безымянные `column_N`, а РЕАЛЬНЫЕ имена колонок лежат в строке 0 данных. `backend/main.py`'s `/api/upload` просто пробует `detect_and_unflatten()` первым для `.xlsx`/`.xlsm` (любая ошибка внутри — молча в `None`, никогда не роняет загрузку), и если он вернул `None` — использует прежний `parse_file_raw()`. `backend/columns.py::promote_header_row()`, `upload.html`, деревья, сверка — не тронуты вообще.
- **11 новых тестов** (`tests/test_hierarchical.py`, синтетический файл собран через `xlsxwriter`, НЕ `openpyxl.Workbook()` — живой факт: `openpyxl`'s собственный писатель для маленького листа пишет инлайн-строки и вообще не создаёт `xl/sharedStrings.xml`, что сделало бы тест на баг с регистром бессмысленным заглушкой) + 1 сквозной HTTP-тест (`backend/tests/test_hierarchical_upload.py`) на полный `upload → columns → entities → summary`.

**Несколько сумм одновременно.** `core/session.py::Session.metric_column` (одна колонка) → `metric_columns: list[str]` — пользователь выбирает одну ИЛИ несколько числовых колонок как «сумма» разом (например «Стоимость» в рублях И «Вес» в кг), каждая сверяется НЕЗАВИСИМО. Тот же приём, что уже был обоснован для нескольких деревьев в прошлой фазе: `core/reconcile.py::rollup()` не тронут вообще, просто вызывается по разу на каждую пару (дерево, метрика).

- **Форма ответа API (решено в этой фазе).** `GET .../summary/{column}` и `GET .../breakdown/{column}` возвращают результат СРАЗУ по всем метрикам одним запросом: `{"metrics": {"Стоимость": {...}, "Вес": {...}}}` для сверки, и одна СЛИТАЯ таблица с колонкой-суммой на каждую метрику (имя колонки — само название метрики, коллизий не бывает: `set_columns()` не даёт одной колонке участвовать в двух ролях разом) для разбивки — вместо N отдельных запросов или перезаписи одной суммы другой.
- **Экспорт**: имена листов расширяют уже существующее правило суффиксов (было только по дереву, теперь и по метрике) — сессия с 1 деревом и 1 метрикой даёт БАЙТ-В-БАЙТ тот же файл, что и до этой фазы (проверено отдельным тестом и живым скачиванием). Пара (дерево, метрика) за пределами самой первой получает суффикс `— {что не первое}` — например 2 дерева × 2 метрики: `Итоги`, `Итоги — Вес`, `Итоги — Клиент`, `Итоги — Клиент — Вес`.
- **`backend/db.py`**: добавлена колонка `metric_columns` (JSONB, nullable) в Проекты — на живом сервере таблица `projects` была пуста (0 строк), поэтому применено как `DROP TABLE` + пересоздание через `create_all()` при рестарте, а не миграция вслепую — проверено `\d projects` на сервере до и после. `metric_column` (в единственном числе) оставлен как первый элемент списка — тот же приём back-compat, что уже был у `entity_column`.
- **Фронтенд.** `upload.html`: роль «Это сумма» была единственной — выбор новой колонки сбрасывал предыдущую (`columnRoles = columnRoles.map(r => r === 'metric' ? null : r)`); убрано, роль ведёт себя как «категоризировать»/«разбивка» — любое число колонок. `app.html`: `fmt()` больше не пришивает знак «₽» намертво (метрика не обязана быть деньгами, например «Вес» в кг) — вместо этого берёт РЕАЛЬНОЕ имя колонки как подпись; везде, где раньше показывалась одна сумма (итог дерева, итог группы, футер сверки, разбивка) — теперь показываются все выбранные суммы рядом через « / » (например «45 000 Стоимость / 12,5 Вес»). Сверка «сошлось» (зелёным) — только когда «Не распределено» = 0 у КАЖДОЙ метрики, не только у первой.
- **26 новых тестов**: `tests/test_session.py` (сверка 2 метрик на одном дереве независимо + отказ на метрику, не выбранную для сессии), `backend/tests/test_multi_metric_api.py` (6 сквозных HTTP-тестов: выбор колонок, сверка, разбивка, 2 варианта именования листов экспорта), плюс каждый существующий тест с одной ролью «сумма» переведён на новый list-based формат запроса. **177/177 тестов** (было 168).

**Понятность для нечеловека-бухгалтера (Задача 3).** Две компактные, скрываемые (localStorage, обёрнуто в try/catch на случай приватного режима браузера) подсказки: на `upload.html` над таблицей превью — «Категория — как папка: можно вкладывать одну в другую сколько угодно раз. «Сумма» можно выбрать не одну, а сразу несколько»; на `app.html` рядом с «+ Новая категория» — тот же приём метафоры плюс конкретный пример («Хотите сгруппировать клиентов по менеджерам?…») и маленькая статичная (не интерактивная) иллюстрация дерева вымышленными именами. ### Консолидация нескольких файлов / нескольких листов одного файла — готово и протестировано (28.09.2026)

Закрывает пп. 2 и 5 каталога услуг («несколько источников» и «объединение листов одного файла») — единственные 2 пункта из 10, остававшиеся спроектированными, но не закодированными (см. предыдущую фазу). Пользователь загружает несколько файлов подряд (или один Excel с несколькими листами) с СОВМЕСТИМОЙ структурой колонок — они объединяются в один датасет ДО экрана выбора ролей колонок, дальше всё работает как обычно (один общий выбор колонок, дерево категорий, сверка) уже на объединённых данных.

- **Архитектурное решение (главное в этой фазе): не отдельный код-путь, а переиспользование уже готового.** `backend/consolidate.py::consolidate_sources()` промотирует заголовок КАЖДОГО источника отдельно (декоративные преамбулы 1С у разных файлов/листов могут отличаться по длине — своя `header_row_index` на источник, это подтверждено уже существующим кодом даже для одного файла), проверяет совместимость состава колонок, добавляет новую колонку **«Источник»**, и возвращает результат в ТОЙ ЖЕ форме, что и `core.parsing.parse_file_raw()` — generic `column_N`, реальные имена колонок сидят в строке 0 данных. За счёт этого весь остальной, уже протестированный конвейер (`upload.html`'s экран выбора ролей + `guessHeaderRow()`, `backend/columns.py::finalize_pipeline_columns()`) работает БЕЗ единой правки: фронтенд получает от нового эндпоинта ответ той же формы, что и обычный `/api/upload`, и просто продолжает по уже рабочему пути. Одна новая концепция переиспользует два уже проверенных экрана вместо того, чтобы городить третий.
- **«Источник» — обычная колонка, не отдельный механизм.** Ведёт себя как любая колонка в уже рабочем механизме ролей: можно сделать «разбивкой» — тогда уже работающий механизм breakdown/множественных метрик автоматически даёт сравнение ПО ИСТОЧНИКАМ = сравнение по периодам, если источники называть периодами («Июнь», «Июль»). Отдельного механизма «сравнение по периодам» нет и не появилось — он получается бесплатно, как и было решено на этапе проектирования.
- **Каждый столбец приводится к Utf8 перед склейкой заголовка** — не срезание угла, а именно то, что уже происходит сегодня на одиночной загрузке, когда декоративный текстовый заголовок сидит в той же физической колонке, что и числовые данные (у Polars один dtype на колонку, так что присутствие текста где угодно в сырой колонке уже приводит её всю к String) — `finalize_pipeline_columns()`'s `normalize_decimal_comma()` уже умеет конвертировать это обратно в число, когда пользователь подтверждает, что это метрика. Здесь этот же, уже проверенный путь просто становится универсальным, поскольку КАЖДЫЙ источник физически получает синтетический текстовый заголовок.
- **Валидация, не угадывание.** Несовместимые источники (разное число или состав колонок) дают понятную ошибку на русском с именами источников («Источник «Июль» несовместим с «Июнь»: 2 колонок вместо 3…») — не молчаливое объединение и не попытка сопоставить колонки по позиции. Заодно исправлен предсуществующий пробел: `POST /api/upload`'s `UnsupportedFileError` раньше отдавал английский текст исключения прямо в HTTP-ответ (сравнил с уже принятым паттерном у `core.tree`'s ошибок — там текст переводится на границе HTTP, а не течёт из домена как есть) — `_translate_unsupported_file_error()` в `backend/main.py` закрывает и этот случай тоже, не только новый.
- **Объединение листов одного файла реализовано ТЕМ ЖЕ механизмом, что и несколько файлов**, не отдельным UI-потоком: `core/parsing.py::list_excel_sheets()` (через `python_calamine` напрямую — у `pl.read_excel()` нет режима «только перечислить листы, не читать данные») определяет, что у загруженного `.xlsx` больше одного листа, и `backend/main.py::upload_batch()` автоматически разворачивает его в ОДИН ИСТОЧНИК НА ЛИСТ (подпись по умолчанию — «имя_файла — Лист»), после чего пользователь работает с уже знакомым списком источников: может переименовать подпись, поменять строку заголовка на источник, или вовсе убрать ненужный лист кнопкой «Убрать источник» — специального «выберите листы» экрана нет, потому что список-источников-с-возможностью-удалить уже даёт то же самое. `core/parsing.py::parse_file_raw()` и `core/hierarchical.py::detect_and_unflatten()` получили новый параметр `sheet_name` для чтения конкретного листа (включая опциональное автораспознавание иерархического 1С-отчёта НА КАЖДОМ листе отдельно).
- **API (решено в этой фазе):** `POST /api/upload/batch` (принимает несколько файлов, парсит каждый как обычно + разворачивает многолистовые Excel-файлы, возвращает `batch_id` + превью КАЖДОГО источника отдельно) → `POST /api/upload/batch/{id}/consolidate` (тело — `sources: [{index, header_row_index, label}]`, где `index` ссылается на источник ВНУТРИ батча, а не на позицию в самом запросе — так убранный на экране источник просто не упоминается, без перенумерации остальных; успешный ответ — session_id той же формы, что у обычного `/api/upload`). `backend/batch_store.py::UploadBatchStore` — Redis-хранилище на 30 минут для батча между двумя шагами (тот же паттерн «токен → байты в Redis», что уже обоснован в `backend/tools_store.py` для многопроцессного деплоя — 2 uvicorn-воркера, любой из двух запросов может попасть на любой воркер).
- **Фронтенд (`upload.html`):** новая ссылка «+ Объединить несколько файлов или листов одного файла» рядом с обычной зоной загрузки → шаг 1 (очередь файлов, можно убрать до отправки) → шаг 2 (карточка на источник: мини-превью с уже знакомым кликом по строке заголовка и `guessHeaderRow()`, редактируемая подпись по умолчанию = имя файла, кнопка «Убрать источник») → «Объединить и продолжить» → ответ той же формы, что у обычного `/api/upload`, передаётся в `enterPickWorkspace()` (вынесена из `handleFile()`, чтобы оба пути — одиночный файл и консолидация — вели в один и тот же, ни разу не изменённый экран выбора ролей колонок).
- **18 новых тестов**: `tests/test_parsing.py` (`list_excel_sheets`, `parse_file_raw(sheet_name=...)` на настоящем 2-листовом `.xlsx` через `xlsxwriter`), `backend/tests/test_consolidate.py` (7 тестов на `consolidate_sources()` — совпадение сумм по каждому источнику отдельно посчитано вручную через `Decimal`, не поверено реализации; несовместимые источники; коллизия имени колонки «Источник»; плохой `header_row_index`), `backend/tests/test_batch_upload_api.py` (8 сквозных HTTP-тестов через `TestClient`+`fakeredis`: полный сценарий upload→consolidate→columns→entities→groups→assign→summary→breakdown с ручным расчётом сумм по каждому периоду, удаление источника по индексу, автораспознавание многолистового файла, несовместимые источники → понятная русская ошибка, неизвестный/протухший `batch_id` → 404). **195/195 тестов** (было 177).
- **Прогнано вживую через Playwright (локально: настоящий FastAPI + настоящий Redis + Chromium, не мок)** — сценарий из задания: 2 синтетических файла «Продажи Июнь»/«Продажи Июль» (одинаковые колонки Товар/Клиент/Выручка, у июньского — декоративная строка перед заголовком, у июльского нет) → консолидация с подписями «Июнь»/«Июль» → категоризация «Товар» (группа «Молочка» = Молоко+Масло) → сверка (Итого 6 734,56 = По группам 3 734,56 + Не распределено 3 000 — Молоко 1234,56(июнь)+1000(июль)=2234,56 и Масло 1500(июль) сошлись в группе, Хлеб+Сыр остались нераспределены) → Разбивка — Товар по «Источник» (Июнь 3934,56 = 1234,56+500+2200, Июль 2800 = 1000+300+1500 — оба посчитаны вручную заранее и совпали) — все числа сошлись, ноль ошибок в консоли кроме уже задокументированного шума (401 от анонимной проверки `/api/projects`, 404 фавикона). Отдельно проверены несовместимые источники (понятная русская ошибка с именами файлов) и удаление проблемного источника кнопкой перед повторной попыткой — консолидация после удаления проходит успешно.
- **Не задеплоено на живой сервер в этой фазе — заблокировано средой выполнения, не решением.** Эта фаза выполнялась в облачной сессии без SSH-доступа к `195.161.62.21` (исходящая сеть идёт только через HTTPS-прокси; прямое TCP-соединение на порт 22 таймаутит, а SSH-ключей в этой среде нет вообще) — то есть тот же шаг деплоя, что во всех предыдущих фазах (`pytest` на сервере + Playwright против `https://sortab.ru`), физически невозможно выполнить из этой сессии. Код закоммичен и запушен в main как обычно; сам деплой (SSH/pscp тем же способом, что в README) и живая проверка на `sortab.ru` остаются на будущее — выполнить из сессии/среды с реальным SSH-доступом к серверу.

Прогнан полный сценарий через Playwright: создание подкатегории → попытка присвоить не-листу (корректно недоступно в списке) → присвоение реальному листу → полное распределение всех значений → сверка «113 700 = группы + 0 не распределено» → попытка удалить непустую группу (заблокирована с понятным сообщением). Ноль ошибок в консоли на всех шагах.

**FastAPI-эндпоинты, связывающие `core/*` с этими экранами, готовы** (см. раздел «FastAPI-бэкенд» выше). Дальше — перенос дизайна в Next.js и реальный HTTP-вызов с фронтенда вместо моковых данных.

## Каталог услуг (10 пунктов, каждый закрывает проверенную боль)

1. Группировка/категоризация (дерево, ручной мэппинг, «ножницы») — ядро
2. Несколько источников (консолидация / сравнение по периодам)
3. Сверка двух файлов на расхождения
4. Развернуть сводную (Unpivot)
5. Объединение листов одного файла как источника
6. Извлечение таблиц из живых (не сканированных) PDF в тот же движок
7. Сравнение PDF (Compare/Redline)
8. Разбивка PDF по маркеру
9. Водяные знаки при скачивании PDF
10. Mail Merge (Excel → N именных PDF-документов)

Все 10 доступны на любом тарифе — тарифы различаются только объёмом (см. монетизацию ниже), не набором услуг.

## Ключевые решения (зафиксированы в обсуждении)

- **Ручной мэппинг, без ИИ на ядре.** Пользователь сам строит дерево групп/подгрупп (произвольная вложенность, значение переносится только в лист — не в промежуточный узел) и вручную распределяет уникальные значения. **Никаких автоматических подсказок объединения похожих значений** — пользователь явно отклонил вариант с подсказками, разнос строго вручную (чекбоксы + bulk-перенос, без единого предложения от алгоритма).
- **Множественные источники.** Можно загрузить несколько файлов сразу — либо консолидировать в один итог, либо сравнивать по периодам (обе механики строятся на одном и том же разобранном наборе данных).
- **Стек (обоснован реальными бенчмарками):**
  - Парсинг файлов — `python-calamine` (Rust-биндинг), покрывает .xls/.xlsx/.xlsm/.xlsb/.ods одной библиотекой — в ~21 раз быстрее openpyxl.
  - Обработка данных — **Polars** (не pandas) — на одинаковой задаче в ~3.9 раза быстрее pandas, измерено локально.
  - Нечёткое сравнение — `RapidFuzz` с блокировкой по извлечённым цифрам перед сравнением (наивное сравнение «каждый с каждым» на 45 000 уникальных значений — 51 сек; с блокировкой — 0.09 сек).
  - CSV-кодировка — автоопределение (UTF-8 → Windows-1251) через `charset-normalizer`, разделитель `;` и десятичная запятая — обязательно для выгрузок из 1С.
  - Очередь задач — Redis + RQ (не Celery — избыточен для целевого сервера).
  - Backend — FastAPI, БД — PostgreSQL.
- **Формат вывода:** два листа — «Детализация» (исходные строки + путь по дереву групп + источник) и «Итоги» (свод с подытогами по каждому уровню, включая явную строку «Не распределено» для сверки).
- **Монетизация (финальная схема — деление по ОБЪЁМУ, не по фичам):** ВСЕ 10 услуг каталога доступны на любом тарифе, включая бесплатный. Три тарифа (см. `design-prototype/index.html` для актуальных цифр): **Бесплатно** (0₽, 1 проект, 20 МБ, 10 PDF-стр/мес) / **Профи** (990₽/мес, 1 человек, безлимит проектов, 100 МБ, 200 PDF-стр/мес) / **Бизнес** (2 990₽/мес, до 5 человек, 500 PDF-стр/мес) — различие «Бизнес» от «Профи» это команда, не объём для одного человека, поэтому щедрость «Профи» не ворует клиентов у «Бизнес». **Реклама остаётся на всех тарифах** — не главный триггер оплаты, реальный крючок это лимиты. Разовая оплата ~199-299 ₽ — способ оплаты (не отдельная линейка).
- **API и «Корпоративный» тариф — сознательно НЕ делаем** (решение 2026-09-27), хотя реальное обоснование существует (агентства, автоматизация по расписанию — та же логика, что у Docparser/Parseur/DaData, см. раздел про жизненный цикл ниже).
- **Не feature-gating, не полный конструктор — фиксированные тарифы + докупка объёма.** Feature-gating отклонён пользователем как нечестное разделение. Полный конструктор тоже отклонён — конкуренты так не делают, паралич выбора для нетехнической аудитории. Докупка объёма сверху («+5 проектов», «+100 PDF-страниц») — для граничных случаев.
- **Архитектура интерфейса:** «Проекты» (сохранённое дерево+словарь под повторяющийся тип отчёта, источники — Excel/CSV/PDF-таблицы равноправны) отдельно от «Инструментов» (разовые утилиты без сохранения — Unpivot, Compare, Mail Merge, Split, Watермарк).
- **Защита накопительных лимитов от абьюза (смена IP/куки).** Разовая обработка файла (без сохранения) — доступна анонимно, тут нечего защищать (лимит на файл не накопительный). А вот сохранение «Проекта» и месячные квоты (PDF-страницы) обязательно требуют email-аккаунта — анонимная сессия физически не может владеть сохранённым проектом. Полностью защититься от множественных email нельзя (как и у любого SaaS), но обход бесплатного лимита стоит абьюзеру повторной ручной пересборки дерева категорий (30-60 мин) — то есть теряется именно та выгода, ради которой стоило бы платить. Доп. меры (снижают шум, не решают полностью): подтверждение email, rate-limit регистраций с одного IP/сутки.
- **Регистрация — «мягкий email», не анонимность и не полная регистрация.** Первая разовая обработка без сохранения — анонимна (вирусный магнит для холодного трафика из поиска/Telegram, порог входа = 0, load-bearing для всей стратегии роста). Сохранение Проекта — только email без пароля/подтверждения на этом шаге (не полноценная регистрация) — минимальное трение, но уже даёт лид-базу и закрывает накопительные лимиты.
- **Лимит файла (20 МБ) — не главный рычаг монетизации.** Конкуренты держат 10-100 МБ на free tier, наши 20 МБ — середина диапазона. Но типичный реальный отчёт (по нашим же бенчмаркам: 20 МБ ≈ 300 000 строк) — это 1-5 МБ, то есть подавляющее большинство обычных пользователей лимит никогда не увидят. Главный рычаг — «1 бесплатный проект», не размер файла. Точное число не критично — смотреть реальное распределение размеров после запуска, не гадать заранее.

## Пробелы, не закрытые монетизацией (нужно решить до платежей, не позже)

- Годовая оплата со скидкой — не заложена, стандартная механика для снижения оттока.
- Политика возврата/отмены — не обсуждена, требуется по закону и для подключения Robokassa.

## Решено: тарифы, жизненный цикл Проектов, API

- **Тарифы (финал, 2026-09-27):** Бесплатно (0₽) / Профи (990₽/мес, 1 человек) / Бизнес (2 990₽/мес, до 5 человек — закрывает командный доступ). **API и «Корпоративный» тариф сознательно НЕ делаем** — отклонено пользователем несмотря на то, что реальное обоснование (агентства, автоматизация по расписанию — та же логика, что у Docparser/Parseur/DaData) существует. Если понадобится позже — обоснование уже есть в истории проекта, переоценивать заново не нужно.
- **Себестоимость тарифов посчитана, не на глаз.** Активный «Профи»-пользователь (20 Excel-заданий + 50 PDF-страниц/мес) = ~3.5 мин вычислений/мес = 0.008% мощности сервера. 500 таких подписчиков = 4% ёмкости при выручке 495 000₽/мес. Дешёвые тарифы не подрывают экономику по прямой себестоимости — реальный ограничитель это пиковая нагрузка (уже закрыта приоритетной очередью), не деньги на вычисления.
- **Жизненный цикл Проектов при неоплате.** Мы храним только Проекты (дерево+словарь — лёгкие структуры), не файлы — хранить их подольше почти ничего не стоит технически, это вопрос политики, не себестоимости. Правило: 3-7 дней грейс-период на неудачную оплату (не наказываем за временно отклонённую карту) → при реальном понижении тарифа лишние Проекты **блокируются, не удаляются** (1 активный, остальные read-only с призывом оформить Профи) → хранятся минимум 90 дней → удаление только после предупреждения по email, если реактивации не было. Никогда не удаляем работу пользователя молча.
- **Десктоп-версия (не сейчас, но реальный будущий SKU).** Подтверждено на конкуренте EasyMorph — они продают десктоп именно за «данные не покидают компьютер, работает air-gapped» и берут за это деньги (платная Pro-подписка). Корпоративная политика «не грузить данные в сторонние сервисы» — реальная, задокументированная практика ИБ, не выдумка. Не делаем сейчас (подорвёт наш нулевой порог входа для основной аудитории), но движок пишется как переиспользуемые Python-модули не завязанные на веб-сервер — десктоп-обёртка позже реалистична, не переписывание с нуля. **Триггер:** когда «не можем загружать в облако» станет повторяющимся возражением в переговорах с крупными клиентами — тогда как отдельный дорогой enterprise-SKU (годовая лицензия), не замена бесплатному вебу. Бонус: снимает самую дорогую нагрузку (большие файлы, частый PDF) с нашего сервера на железо клиента.

## Фаза 3 — небольшие доработки поверх готового движка (подтверждены пользователем)

- **Сверка взаиморасчётов между двумя файлами** — тот же движок fuzzy-match + ручной мэппинг с памятью, вывод — список расхождений вместо суммы по группе.
- **Объединение нескольких листов одного файла** как ещё одного источника (тот же механизм «несколько источников», что уже спроектирован для консолидации/сравнения периодов).
- **Разворот сводных таблиц (Unpivot/Reverse Pivot)** — `pandas.melt`/эквивалент в Polars: превращает двумерную сводную таблицу (товары строками, месяцы столбцами) в плоский список для загрузки в 1С/CRM. Реальная массовая боль, технически копеечно.
- **Генератор документов из Excel (Mail Merge)** — пользователь размечает переменные в своём PDF/Word-шаблоне договора, загружает Excel на N строк, получает архив из N именных PDF-договоров. Отдельный по объёму модуль, не «заодно» с ядром.
- **Умная разбивка PDF по маркеру** — большой PDF (сотни страниц, накладные разных клиентов подряд) режется на отдельные файлы по повторяющемуся текстовому маркеру («УПД №», смена ИНН), автоматически именуется. Детерминированный код, без ИИ.
- **Динамические водяные знаки при скачивании** — при скачивании PDF/прайс-листа из личного кабинета на каждую страницу накладывается прозрачный водяной знак с ID/именем/IP скачавшего сотрудника — защита от слива баз данных для дистрибьюторов.

## PDF — отдельное направление (не «заодно» с Excel-ядром)

- **Сравнение документов (Compare/Redline)** — единственная PDF-фича из «дорогих премиум» идей, признанная стоящей: свободная ниша (ни iLovePDF, ни Smallpdf так не делают), детерминированный текстовый diff по координатам, без ИИ.
- **Извлечение таблиц из «живых» (не сканированных) PDF** в тот же движок группировки — конкуренты (iLovePDF/Smallpdf) сами ломают такие таблицы и оставляют пользователя разбираться в сыром Excel; мы можем отдавать кривой результат прямо в уже готовый экран ручной разметки.
- **PDF со сканов (OCR + ручная разметка рамок на изображении)** — технически возможно без оплаты AI-токенов (Tesseract — не LLM), но это ЗАМЕТНО более сложный отдельный модуль (предобработка изображений, борьба с перекосом скана) — не решено, не в плане, требует отдельной оценки, если возникнет спрос.

### PDF — реально протестировано (не только описание библиотек, как раньше)

Собрал синтетический «счёт»-PDF (реальный текстовый слой, кириллица, без линий-границ — как большинство настоящих накладных) и прогнал через `pdfplumber` и `camelot`, тем же уровнем строгости, что и Excel-бенчмарки:
- **`pdfplumber` в дефолтной конфигурации — 0 извлечённых строк** и на 3000, и на 20 000 строках. Дефолтная стратегия ищет линии-границы таблицы, а на счетах без явных границ это не работает вообще. Нужна явная настройка (`vertical_strategy="text"`), не «из коробки».
- **`camelot` (flavor=stream) — работает и даёт верные данные.** Проверил результат посимвольно по кодам Unicode (не доверяя выводу в консоль Windows, которая манглит кириллицу) — значения извлекаются точно, без потерь и сдвигов по колонкам.
- **Но заметно медленнее Excel.** 20 000 строк / 556 страниц — **34.3 сек** на сильной машине (i5-12600K). С поправкой на целевой сервер (слабее в 3-4 раза) — реалистично **~100-140 сек** на такой объём. PDF-квоты/таймауты очереди нужно закладывать с этим числом, не ожидать той же мгновенности, что у Excel.
- **Проверил и отклонил «более быстрые» альтернативы.** Нашлись Rust-библиотеки с заявлениями «в 10-50 раз быстрее» (pdfsink-rs, pdf_oxide, tablers), но с тревожными признаками: несколько никак не связанных GitHub-аккаунтов (`Mu-L`, `firecrawl`, `pinegap-tech`) публикуют репозиторий с одинаковым названием и текстом описания — похоже на спам/клоны, не независимые проекты. Не беру в стек без реальной проверки на практике. **PyMuPDF тоже проверил и отклонил** — в их же репозитории задокументирован баг: `find_tables()` у PyMuPDF медленнее, чем у pdfplumber ([GitHub issue #2885](https://github.com/pymupdf/PyMuPDF/issues/2885)).
- **Проверил параллелизм внутри одного задания — и ОТКЛОНИЛ его для продакшена.** Camelot обрабатывает страницы независимо, распиливание документа на 3 параллельных процесса даёт 34.3с → 21.7с (~1.6x, не 3x — накладные расходы на старт процессов съедают часть выигрыша). Технически работает, но **это неправильная оптимизация при множестве одновременных пользователей**: пока все 3 ядра заняты одним PDF одного человека, все остальные (включая API и БД) простаивают. Правильно — держать каждое задание одноядерным, параллелить РАЗНЫЕ задания РАЗНЫХ пользователей через очередь (см. раздел про пропускную способность ниже), а не одно задание одного пользователя через все ядра.

## Пропускная способность при множестве одновременных пользователей (100-1000, не один человек)

Посчитал не скорость одного запроса, а сколько заданий в секунду выдерживает сервер целиком — это другая задача и другой ответ. При 2 воркерах (по одному ядру, третье — под API/БД/Nginx), каждое задание одноядерное:

| | Время/задание | Пропускная способность (2 воркера) |
|---|---|---|
| Excel/CSV | ~10 сек | 0.2 задания/сек ≈ 720/час |
| PDF | ~120 сек | 0.017 задания/сек ≈ 60/час |

**Честная оценка нагрузки:** 1000 одновременно активных пользователей, каждый отправляет файл на обработку в среднем раз в 5 минут (консервативно — большую часть времени человек просто кликает в интерфейсе, не грузит сервер) — это ~3.3 задания/сек по системе. Против пропускной способности 0.2/сек по Excel — **разрыв в ~16 раз**, по PDF — почти в 200 раз. При 100 пользователях разрыв тоже есть (0.33 нужно против 0.2 есть), но не катастрофический.

**Вывод: один сервер 3×2ГГц/10ГБ не расcчитан на настоящую 1000 одновременно активных пользователей — и не должен быть на старте.** Хорошая новость: стек (RQ + Redis) изначально поддерживает горизонтальное масштабирование без переделки архитектуры — воркеры RQ можно запускать на любом количестве отдельных серверов, если все смотрят в один Redis, они работают как единый пул без доп. координации ([rq/rq на GitHub](https://github.com/rq/rq)). Операционное правило вместо гадания: мониторить p95 времени ожидания в очереди после запуска — превысило ~30 сек для Excel / ~3 мин для PDF → добавить ещё один воркер-сервер, указывающий на тот же Redis. Не строить под 1000 пользователей заранее, раз их пока нет.

### Важная поправка: «доход растёт вместе с нагрузкой» — верно только для ПЛАТНЫХ пользователей

Пользователь верно поймал слабое место: у нас есть бесплатный тариф, а виральный рост (наша же стратегия) означает, что бесплатных пользователей на старте всегда на порядок больше платных — и они грузят сервер точно так же, но приносят копейки (реклама) или ничего. «Сервера появятся вместе с деньгами» — справедливо для платного трафика, но не для бесплатного, который и есть основной источник нагрузки при вирусном росте.

**Что уже защищает (заложено случайно, но удачно):** PDF — самая дорогая операция (~120с против ~10с у Excel) — на бесплатном тарифе квота всего 10 PDF-страниц/мес против 200 у «Профи», то есть самая тяжёлая нагрузка структурно придавлена именно там, где трафика больше всего.

**Реализовано 2026-09-27:** приоритет в очереди для платящих — `core/queues.py`, две именованные RQ-очереди (`paid`/`free`), воркер слушает их в этом порядке и полностью вычищает `paid`, прежде чем тронуть `free` — это штатное поведение RQ, не самодельный костыль ([python-rq.org](https://python-rq.org/docs/workers/)), но перепроверено собственным тестом через fakeredis, не принято на слово: платное задание, поставленное в очередь вторым, реально выполняется первым (`tests/test_queues.py`, 2/2). Известный и принятый компромисс: это жёсткий приоритет, не round-robin — при непрерывном потоке платных заданий бесплатные теоретически могут ждать долго. При нашем масштабе (платных меньшинство) это правильный дефолт, пересматривать только если реальный мониторинг покажет голодание бесплатных даже при слабой платной нагрузке.

### Реальная ёмкость текущего сервера (не оценка на глаз)

**Поправка 2026-09-27: прошлая оценка PDF считала throughput по огромному документу (556 страниц), а не по реальной бесплатной квоте.** Измерил честно маленький файл (9 страниц, ровно размер бесплатной квоты) — **0.38 сек** на дев-машине, ~1-1.5 сек на целевом сервере. Это на два порядка дешевле, чем цифра, которую я раньше заложил в таблицу throughput — бесплатный PDF дешёвый ПО КОНСТРУКЦИИ (квота 10 стр. не даёт разрастись), а дорогой сценарий — это большой документ (до 200 стр.) от ПЛАТЯЩЕГО пользователя, что уже компенсируется оплатой и защищено приоритетной очередью.

Через целевую загрузку очереди 70% (выше — время ожидания растёт нелинейно по теории массового обслуживания):

| | Пропускная способность | Безопасный поток (70%) |
|---|---|---|
| Excel/CSV | 12 заданий/мин | 8.4 заданий/мин |
| PDF, маленький документ (≤10 стр., бесплатный размер) | ~80-120 заданий/мин | ~56-84 заданий/мин |
| PDF, большой документ (≤200 стр., платный размер) | ~1 задание/мин | 0.7 заданий/мин |

**Практический ориентир:** сервер уверенно тянет ~40-120 одновременно активных пользователей на Excel-нагрузке — хороший запас для старта. Бесплатный PDF (маленькие документы) — НЕ узкое место, дешевле Excel. Узкое место — большие PDF от платящих (~3-11 одновременных), но это уже оплаченная и приоритезированная нагрузка, а не массовый бесплатный трафик. **Убирать PDF из бесплатного тарифа не нужно** — сама квота уже держит стоимость низкой, а полное удаление вернуло бы деление по фичам, от которого пользователь сам отказался раньше.

**На запуске (первые недели/месяцы) волноваться о ёмкости вообще преждевременно** — расчёты выше это потолок при уже развитом трафике (десятки-сотни одновременных), а на старте будет на порядки меньше посетителей. Это расчёт по теории очередей на основе измеренного времени задачи, не нагрузочный тест — после запуска сверять с реальной очередью, не верить таблице вслепую.

## Rate limiting (сделано 2026-09-27, живьём нагружено, не на слово)

**Проблема, которую закрывали:** до реального домена сайт висел на голом IP — не страшно. С доменом это меняется, а анонимные тяжёлые эндпоинты (`/api/upload`, весь `/api/tools/*`) выполняются СИНХРОННО прямо в обработчике FastAPI (camelot/полярс/reportlab — блокирующий код внутри `async def`, не вынесено в RQ-очередь несмотря на то что `core/queues.py` для этого уже есть — сама очередь пока подключена только к другому пути, не к этим HTTP-эндпоинтам) при всего **2 uvicorn-воркерах** (`--workers 2`, см. `systemctl cat gruper-backend`) на 3-ядерном сервере. Значит горстка параллельных тяжёлых запросов с одного источника способна занять оба воркера на десятки секунд и положить сайт для всех остальных.

**Реализовано только на уровне nginx** (`/etc/nginx/sites-available/gruper` на сервере — не в git, конфиг ниже для истории):
```
limit_req_zone $binary_remote_addr zone=heavy:10m rate=10r/m;   # /api/upload + /api/tools/* — burst=4, nodelay
limit_req_zone $binary_remote_addr zone=api:10m   rate=300r/m;  # весь остальной /api/ (session/entities, summary, groups, auth, projects) — burst=60, nodelay
limit_req_status 429;
```
429 отдаёт не голую nginx-страницу, а JSON в том же формате, что и обычные ошибки FastAPI: `{"detail":"Слишком много запросов. Подождите немного и попробуйте снова."}`.

**Почему только nginx, без дублирующей защиты в FastAPI (осознанный выбор, не «оба на всякий случай»):** бэкенд слушает только `127.0.0.1:8000` — единственный вход снаружи это nginx, обойти его нельзя. nginx режет запрос на уровне C ещё ДО того как тело multipart-запроса вообще прочитано и до того как занят воркер uvicorn — именно то, что нужно против флуда тяжёлых аплоадов при пуле из 2 воркеров. Добавление второго Redis-лимитера в Python не даёт защиты РАНЬШЕ nginx (тот же единственный вход) и не спасает воркер-пул лучше — к моменту, когда python-код успел бы проверить лимит, request уже занял воркер. Дублирование только развело бы два набора порогов, которые придётся держать в синхроне.

**Числа выбраны не на глаз, а по замеренной пропускной способности** (раздел «Пропускная способность» выше): система целиком тянет ~12 Excel-заданий/мин и ~1 большое PDF-задание/мин при 2 воркерах. Лимит heavy-зоны (10 запросов/мин на IP, burst 4) — заметно ниже системного потолка по Excel, чтобы один источник не мог в одиночку занять всю ёмкость сервера, но burst даёт пользователю без штрафа опробовать несколько файлов/инструментов подряд (реальный сценарий — см. проверку ниже).

**Реально нагружено против живого сервера** (`ratelimit_test.py`, реальные HTTP-запросы на `195.161.62.21/api/upload` с настоящим CSV-фикстурой):
- Обычное использование (5 запросов с интервалом 8с — имитация «загрузил файл, посмотрел, загрузил другой») — **0 из 5 получили 429**.
- Флуд (25 запросов подряд без пауз) — первые 5 прошли (burst), дальше **18 из 25 получили 429**, прошли только те, что попали в естественный «протёк» бакета (~1 запрос/6с). Ни один флуд-запрос не обошёл лимит.
- 30 быстрых подряд запросов к лёгкому эндпоинту (`api`-зона) — 0 заблокировано, подтверждает что обычное интерактивное дерево категорий (частые `/entities`, `/summary`) лимитом не задето.
- Полный live-сценарий через Playwright по настоящему UI (`upload.html` → выбор колонок → `app.html`, дерево категорий) против `195.161.62.21` **после** включения лимитов — все 6 реальных API-вызовов сессии (`upload`, `columns`, `groups`, `entities`, `summary`) вернули 200/401(ожидаемо для анонимной сессии), ни одного 429.
- `pytest` из корня — 144/144, без изменений (эти тесты бьют по `TestClient`+`fakeredis`, live nginx их не касается).

**Не закрыто этим проходом (отдельная задача на будущее, не rate limiting):** у анонимных `/api/tools/*` до сих пор нет реального лимита на число PDF-страниц за запрос (лимит 20 МБ по размеру файла есть, лимит по числу страниц — нет) — крупный PDF (сотни страниц) технически можно прогнать даже одним легитимно редким запросом, и это будет медленно (~100-140с по бенчмарку camelot). Это вопрос месячных квот/привязки к тарифу (см. «Пробелы, не закрытые монетизацией» выше), а не rate limiting — сознательно не трогал в этом проходе.
